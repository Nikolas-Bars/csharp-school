# Архитектура — как на большом проекте

Правила ниже не пожелания. Большую часть проверяют автоматически (PHPStan с правилами проекта,
ESLint, vue-tsc, тесты), и `make check` не проходит при нарушении. То, что не проверяется
автоматически, проверяется на ревью (`review.md`). Нарушение без явного согласия пользователя
недопустимо; если правило мешает — сначала обсудить и поменять правило, потом код.

## Общее

- **Модульный монолит.** Бэкенд один, но каждый модуль пишется так, чтобы его можно было
  вынести в отдельный сервис, не переписывая остальные. Заранее ничего не выносить.
- **Код учеников выполняется только в браузере ученика** (`runner`, WebAssembly).
  Сервер не компилирует и не запускает присланный код ни в каком виде. Сервер принимает
  только результат проверки и текст решения — как данные.
- **Один формат ответа API:** `{ status, message, data, errors }`.
- **Всё, что читает человек, переводится:** бэкенд `lang/{ru,en}/`, фронт
  `src/i18n/locales/{ru,en}.json`. Строк литералами в интерфейсе нет.
- **Строгая типизация везде:** PHP `declare(strict_types=1)` + PHPStan level 10,
  TypeScript strict + vue-tsc, C# `<Nullable>enable</Nullable>` + предупреждения как ошибки.
- **Секреты** — только в `.env` бэкенда и не в git. Всё `VITE_*` попадает в публичный бандл.
- **Тесты обязательны:** на каждый контроллер — feature-тест, на каждую чистую функцию и
  стор — unit-тест, на каждую задачу курса — тест эталона и неверных решений.

## Бэкенд (`backend`)

Подробно — `backend/ARCHITECTURE.md`. Коротко:

- Модуль — `app/Modules/{Module}/`, имя в единственном числе (`User`, `Auth`, `Course`,
  `Progress`).
- Поток: `Request → Controller → DTO → Action → Task → Repository → Model`, ответ —
  `ApiResponder` + `Resource`.
- Контроллер — один `__invoke`, вызывает **один** Action. Action не вызывает Action.
  Task — одна атомарная операция. В БД ходит **только** Repository.
- Модуль владеет своими таблицами. Чужие модули — только через `Contracts/` (интерфейс + DTO)
  и доменные события с ID и скалярами. Ссылка на чужое — ID без внешнего ключа
  (исключение — `user_id` на `users`).
- Узел без состояния: файлы через `Storage::disk()`, кэш и лимиты в Redis, ничего в памяти
  процесса между запросами (RoadRunner держит процесс живым).
- Списки — курсорная пагинация; счётчики — в строке-владельце, `increment`.
- Ломающие изменения API — новым полем или эндпоинтом.

## Фронтенд (`frontend`)

Подробно — `frontend/CLAUDE.md`. Коротко:

- Слои и папки:
  - `src/api/` — **один файл на модуль бэкенда**; весь HTTP только через `api/http.ts`;
  - `src/types/` — типы ответов API, зеркалят ресурсы бэкенда;
  - `src/stores/` — Pinia, единственный владелец состояния своей области;
  - `src/composables/` — переиспользуемая логика с реактивностью (`useXxx`);
  - `src/components/ui/Base*.vue` — общие базовые компоненты без бизнес-логики;
  - `src/components/{feature}/` — компоненты фичи;
  - `src/components/layout/` — оболочка приложения (шапка, переключатель темы);
  - `src/views/*View.vue` — страницы маршрутов, лениво загружаются роутером;
  - `src/router/` — маршруты и правила доступа (`meta`);
  - `src/i18n/` — языки и тексты; `src/theme/` — реестр тем;
  - `src/runner/` — мост к `runner` (Web Worker), без Vue;
  - `src/utils/` — чистые функции без состояния.
- Направление зависимостей: `views → components → composables/stores → api → http`.
  Компонент не вызывает `fetch` и не ходит в `api/` напрямую — через стор или composable.
  Фича не импортирует внутренности другой фичи; общее — в `components/ui`, `utils`, `types`.
- Компоненты: `<script setup lang="ts">`, типизированные `defineProps` / `defineEmits` /
  `defineModel`, `scoped` стили, только токены (`frontend-styles.md`).
- Доступность: настоящие `<button>`, `<a>`, `<label>`; `aria-label` у кнопок-иконок;
  кнопки ≥ 44 px; всё доступно с клавиатуры.
- Тяжёлое (компилятор C#, редактор кода) грузится лениво и работает в Web Worker, чтобы не
  блокировать интерфейс.

## Runner (`runner`)

Подробно — `runner/CLAUDE.md`. Коротко:

- .NET-проект: Roslyn компилирует код ученика, сборка выполняется в том же WebAssembly-рантайме;
  Console перехватывается (ввод, вывод с лимитом), проверки задачи идут против результата.
- Ядро (`Runner.Core`) не зависит от браузера: те же компиляция, запуск и проверки работают в
  тестах на обычном .NET — и будут работать в тестах курса (эталоны и неверные решения).
- Работает только в Web Worker: зависание кода ученика (бесконечный цикл) лечится перезапуском
  воркера по таймауту, интерфейс не страдает. Таймаут считается с начала выполнения кода
  ученика, не с загрузки .NET.
- Наружу — узкий типизированный протокол (`compile`, `run`, `test` → диагностика, вывод,
  исключение со строкой, результаты проверок). Типы зеркалятся во фронте (`src/runner/protocol.ts`).
- Сообщения компилятора переводятся на понятный русский по коду ошибки (`CS0103` и т. п.) на
  фронте (`compiler.*` в локалях), оригинал показывается рядом; порядок аргументов закреплён
  тестами runner (`CommonMistakesTests`).
- Сборка — в Docker-образе .NET SDK (`make build`), результат копируется в
  `frontend/public/runner/` (в git не попадает).
- Однопоточный WebAssembly ломает то, что работает на обычном .NET (ожидание задач, рефлексия,
  Console.In). После изменений в ядре — проверка в браузере (`/dev/runner` во фронте).
